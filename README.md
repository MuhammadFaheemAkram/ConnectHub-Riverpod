A focused rebuild of the **ConnectHub** social app's core slice with **Riverpod 3** for state management *and* dependency injection, built with Flutter 3.47 and Dart 3.13.

The slice covers:
- the feed;
- a post with its comments;
- creating a post;
- search;
- notifications;
- profiles;
- settings.

Like the original, everything runs on a **fake, in-memory backend**: no API key, no server.

> **Why this repo exists**
>
> [ConnectHub-Flutter](https://github.com/MuhammadFaheemAkram/ConnectHub-Flutter) builds the same features with **Bloc** (Cubits, plus Blocs where events earn their place) and **get_it + injectable**. This edition keeps the **domain and data layers the same** and rewrites the **presentation layer and the DI** in idiomatic Riverpod, so the comparison isolates what Riverpod changes:
> - **providers as the dependency graph**, overridden in tests, with no service locator;
> - **`Notifier` / `AsyncNotifier`** for screen state, with `AsyncValue` for loading, error and data;
> - **families** and **auto-dispose** for parameterized, screen-scoped state;
> - **side effects** through `ref.listen`, and `ref.mounted` after every async gap;
> - **debounced search through disposal**, without a stream library.
>
> It is the Flutter counterpart of the native "architecture editions": [ConnectHub-MVI](https://github.com/MuhammadFaheemAkram/ConnectHub-MVI) (Android) and [ConnectHub-TCA](https://github.com/MuhammadFaheemAkram/ConnectHub-TCA) (iOS). The final `docs/BLOC_VS_RIVERPOD.md` compares the two Flutter editions screen by screen.

## 🏛️ Architecture

The same layers as ConnectHub-Flutter. The presentation layer and the DI are what change:

```
Widget (ConsumerWidget)
   │  ref.watch(provider)          ← rebuilds when the state changes
   │  ref.read(provider.notifier)  ← calls an intent: like(id), refresh()
   ▼
Notifier / AsyncNotifier  (screen state; auto-dispose; a family per id)
   │  ref.read(useCaseProvider)
   ▼
Use case → Repository  (domain contracts; data implementations)
   │
   ├─▶ drift (the offline cache; streams the UI watches)
   └─▶ fake API services → in-memory FakeServer
```

ConnectHub-Flutter for comparison: `View → Cubit/Bloc → UseCase → Repository`, wired with `get_it`.

**The provider graph after Phase 4** (details in [the Phase 2 summary](docs/PHASE_2_SUMMARY.md)):

```
ProviderScope (main.dart; automatic retry off)
├── appRouterProvider                keepAlive   GoRouter
├── clockProvider                    keepAlive
├── networkSimulatorProvider ─┐      keepAlive   latency, "Simulate network failure"
├── fakeServerProvider ───────┤      keepAlive   the backend's data
├── feedApiServiceProvider ◀──┘      keepAlive
├── databaseConnectionProvider       keepAlive   a file (in tests: in memory)
├── appDatabaseProvider              keepAlive   closed on dispose
├── feedRepositoryProvider           keepAlive   cursor paging
├── postRepositoryProvider           keepAlive   a post, a new post, optimistic likes and saves
├── commentRepositoryProvider        keepAlive   comments; optimistic delete and like
├── searchRepositoryProvider         keepAlive   search, results by id, recent searches
├── notificationRepositoryProvider   keepAlive   the server's read state
├── signedInUserIdProvider           keepAlive   'u_demo' (who "mine" is)
├── …UseCaseProviders                auto-dispose
├── feedPostsProvider                auto-dispose   drift stream
├── feedControllerProvider           auto-dispose   AsyncNotifier<FeedState> ← FeedPage
├── postDetailControllerProvider(id) auto-dispose family  ← PostDetailPage
│     └── cachedPostProvider(id), postCommentsProvider(id)  stream families
├── createPostControllerProvider     auto-dispose   Notifier<CreatePostState> ← CreatePostPage
├── searchQueryControllerProvider    auto-dispose   Notifier<SearchState> ← SearchPage
├── currentSearchResultsProvider     auto-dispose   Notifier<SearchResultsView> (synchronous)
│     └── searchResultsProvider(q) ← searchPeople(q) / searchPosts(q) ← searchHits(q): ref.debounce(300 ms)
├── notificationsControllerProvider  auto-dispose   AsyncNotifier ← kept alive by the shell's ref.listen
└── unreadNotificationCountProvider  auto-dispose   Stream<int> (drift COUNT) → the tab badge
```

## 🧪 Testing

- **Notifiers without widgets:** `ProviderContainer.test()` with fake repositories as `overrides`, and every state recorded in order (`FeedController`: the cache then the refresh, loading → error → "Try again", load more, a failed like, a late answer after the Feed is gone).
- **The provider graph:** it resolves; an override reaches everything built on it, in one container only; what is kept alive and what isn't.
- **The data layer on the real graph:** the fake server, drift (in memory), the repositories (paging, optimistic writes, rollback, one request at a time).
- **Families:** each post id its own controller; leaving one post disposes its controller and its queries, not another's.
- **Debounce in fake time:** three keystrokes, one search; no timer left; the previous results kept while the next query waits.
- **Migrations:** every schema version migrates to the latest, and a cached feed survives v1 → v2 row for row.
- **Pages and flows:** the Feed in every state with fake repositories; flows on the real stack (a like the server keeps or refuses, scrolling to the end, offline with and without a cache).
- **The accessibility tour:** every screen and state, light and dark, at 200 % text.
- **Architecture rules:** the domain is plain Dart; only `core/network/` knows the fake server; widgets never reach the data layer; no legacy providers.

**433 tests** after Phase 4.

## 🌐 Fake API and persistence

- **The fake backend:**
  - an in-memory `FakeServer`, seeded from `assets/json/` (ConnectHub-Flutter's seed, without chat);
  - seed times shifted so the newest record is always five minutes old;
  - the demo user `u_demo` is always signed in.
- **The network:**
  - every request crosses a `NetworkSimulator`: 350–700 ms of latency in the app (none in tests);
  - a switch fails every request (Settings → Developer, in Phase 5).
- **Offline-first:**
  - screens render drift (SQLite) only; repositories refresh drift from the API;
  - cached posts show at once and offline;
  - likes, saves, comment likes and deleted comments change drift first, then the server, and are rolled back if it refuses;
  - the schema is versioned (v2: comments; v3: recent searches, notifications), with generated, tested migrations.

| Edition | Repo |
|---|---|
| Android, MVI (Kotlin, Compose, Hilt, Room) | [ConnectHub-MVI](https://github.com/MuhammadFaheemAkram/ConnectHub-MVI) |

| Concept | Android (MVI) | iOS (TCA) | Flutter (Bloc) | **Flutter (Riverpod)** |
|---|---|---|---|---|
| Screen state | `ViewModel` + reducer | `Reducer` + `State` | `Cubit` / `Bloc` | **`Notifier` / `AsyncNotifier`** |
| User actions | `Intent` | `Action` | methods / events | **methods on the notifier** |
| One-off effects | `Effect` channel | `Effect` | `BlocListener` | **`ref.listen`** |
| DI | Hilt | `@Dependency` | `get_it` + `injectable` | **providers + `overrides`** |
| Scoping | `ViewModel` scope | `Store` scope | `BlocProvider` | **auto-dispose; `keepAlive`** |
| Tests | reducer tests | `TestStore` | `bloc_test` | **`ProviderContainer.test()`** |
